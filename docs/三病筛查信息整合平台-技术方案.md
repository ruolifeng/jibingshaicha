# 三病筛查信息整合平台 — 技术方案

## 1. 项目背景与目标

### 1.1 背景

目前三类病种（结核、艾滋病、包虫病）筛查数据分散在三个独立系统中，基层工作人员和患者无法在一个入口查看「同一人三类筛查完成情况」，现场筛查时也缺少快速识别「未检项目」的手段。

### 1.2 建设目标

| 目标         | 说明                                                           |
| ------------ | -------------------------------------------------------------- |
| **信息整合** | 新建统一 Web 平台，按身份证号聚合展示三类病种筛查概况          |
| **接口对接** | 三个源系统各提供独立接口，本平台按需抓取汇总信息（非全量同步） |
| **现场提醒** | PDA 刷身份证，即时展示该患者三类筛查缺失项并引导检查           |
| **可扩展**   | 架构预留 App / 小程序接入能力                                  |

### 1.3 不在本期范围（建议明确）

- 不替代三个源系统的业务录入与全流程管理
- 不做三个源系统的数据双向写回（除非后续单独立项）
- 不做复杂统计分析、报表中心（可二期）

│                    统一整合平台（新建）                        │
│  Web 管理端  │  PDA 现场端  │  （预留 App/小程序）              │
└──────────────┬──────────────────────────────────────────────┘

       ┌───────┼───────┐

  │ 结核筛查 │ │ 艾滋病   │ │ 包虫病   │

## 4. 总体架构设计

### 4.1 推荐架构：「整合中台 + 轻量缓存」

```
                    ┌──────────────────┐
                    │   用户访问层      │
                    ├──────────────────┤
                    │ Web 管理端        │
                    │ PDA 现场端(H5/原生)│
                    │ (预留 App/小程序) │
                    └────────┬─────────┘
                             │ HTTPS + JWT
                    ┌────────▼─────────┐
                    │  整合平台 API 层   │
                    │  Spring Boot 3.x  │
                    ├──────────────────┤
                    │ 患者聚合服务       │
                    │ 筛查状态判定服务   │
                    │ 提醒规则引擎       │
                    │ 同步调度服务       │
                    └────────┬─────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ 结核适配器 │  │ 艾滋适配器│  │ 包虫适配器│
        └────┬─────┘  └────┬─────┘  └────┬─────┘
             │             │             │
        源系统 API    源系统 API    源系统 API
              │             │             │
        ┌─────▼─────────────▼─────────────▼─────┐
        │           MySQL（整合库）               │
        │  患者主索引 / 筛查快照 / 提醒记录 / 日志  │
        └────────────────────────────────────────┘
```

**设计要点**：

1. **适配器模式**：三个源系统接口格式可能不同，各自封装 Adapter，对外统一领域模型。
2. **本地快照表**：存储最近一次同步的汇总数据，保证列表查询性能；PDA 刷证可「本地优先 + 源系统兜底」。
3. **与现有结核系统技术栈一致**：Vue 3 + Vite + Element Plus + Spring Boot + MyBatis-Plus，降低团队交付成本。

### 4.2 数据同步策略（两档可选）

| 模式                        | 说明                                                           | 适用                       |
| --------------------------- | -------------------------------------------------------------- | -------------------------- |
| **A. 定时同步（推荐一期）** | 每 15min~1h 按增量拉取；PDA 刷证查本地，必要时触发单条实时刷新 | 源系统压力大、网络不稳定   |
| **B. 实时透传**             | 每次查询实时调三个接口聚合                                     | 数据强实时、源系统性能足够 |

**建议一期采用 A**，PDA 刷证时对当前身份证触发 **单条实时刷新**（超时则展示本地缓存并标注「数据可能非最新」）。

## 5. 统一数据模型设计

### 5.1 主键与关联规则

- **主键**：`idNumber`（18 位身份证号，统一大写 X）
- **辅助键**：`name` + `birthDate` 用于冲突校验（同名异人）
- **病种维度**：`diseaseType = TB | AIDS | ECHINOCOCCOSIS`

### 5.3 管理状态枚举（建议统一映射）

| 统一状态        | 含义                  | 映射来源（示例）      |
| --------------- | --------------------- | --------------------- |
| `NOT_SCREENED`  | 无记录 / 未筛查       | 源系统查无此人        |
| `IN_MANAGEMENT` | 在管 / 追踪中         | 类似现有 `archived=0` |
| `COMPLETED`     | 本轮筛查已完成        | 所有必检项完成        |
| `HISTORY`       | 历史 / 已结案         | 类似现有 `archived=1` |
| `UNKNOWN`       | 源系统异常 / 无法判定 | 接口失败              |

## 6. 三个源系统接口规范（建议统一契约）

> 若源系统由不同厂商开发，建议以 **《三病筛查数据对接规范 v1.0》** 形式下发，要求各系统按同一契约实现。

### 6.1 通用约定

| 项目   | 规范                                                   |
| ------ | ------------------------------------------------------ |
| 协议   | HTTPS                                                  |
| 格式   | JSON，`{ code, data, msg }`（与现有系统一致）          |
| 鉴权   | `Authorization: Bearer <token>` 或 API Key + IP 白名单 |
| 时间   | ISO 8601，`yyyy-MM-dd'T'HH:mm:ss`                      |
| 身份证 | 18 位，传输建议脱敏日志                                |

### 6.2 各系统需提供的接口（最少 3 个）

#### 接口 1：按身份证查询患者汇总

```
GET /api/v1/integration/patient/summary?idNumber={idNumber}
```

**响应字段（建议最小集）**：

| 字段           | 类型     | 必填 | 说明               |
| -------------- | -------- | ---- | ------------------ |
| idNumber       | string   | 是   | 身份证号           |
| name           | string   | 是   | 姓名               |
| gender         | string   | 否   | 性别               |
| birthDate      | string   | 否   | 出生日期           |
| phone          | string   | 否   | 联系电话           |
| address        | string   | 否   | 现住址             |
| manageStatus   | string   | 是   | 在管/历史/未筛查等 |
| lastScreenDate | string   | 否   | 最近筛查日期       |
| screenResult   | string   | 否   | 最近筛查结果       |
| completedItems | string[] | 是   | 已完成检查项       |
| pendingItems   | string[] | 是   | 未完成检查项       |
| populationType | string   | 否   | 人群分类           |
| orgName        | string   | 否   | 管理机构           |
| updatedAt      | string   | 是   | 源系统最后更新时间 |

#### 接口 2：增量同步列表（供定时任务）

```
GET /api/v1/integration/patient/changes?since={datetime}&page={n}&size={m}
```

返回自 `since` 以来有变更的患者身份证列表 + 汇总信息。

#### 接口 3：健康检查

```
GET /api/v1/integration/health
```

### 6.3 若源系统无法提供 pendingItems

由整合平台维护 **「必检项规则表」**，根据病种 + 人群 + 年度 + 源系统已完成项 **计算缺失项**（规则引擎，可配置化）。

## 8. PDA 现场端方案

### 8.1 终端选型

| 方案                 | 优点                    | 缺点                      | 建议                  |
| -------------------- | ----------------------- | ------------------------- | --------------------- |
| **Android PDA + H5** | 开发快、与 Web 共用接口 | 依赖网络、读卡 SDK 需适配 | **一期推荐**          |
| Android 原生 App     | 读卡稳定、可离线缓存    | 开发量更大                | 二期                  |
| 微信小程序           | 推广方便                | 身份证读卡硬件支持弱      | 不适合 PDA 刷证主场景 |

### 8.2 PDA 核心流程

```
开始
  │
  ▼
读取身份证（NFC/二代证阅读器 SDK）
  │
  ▼
调用 POST /api/v1/pda/scan
  { idNumber, name, operatorId, siteId }
  │
  ▼
整合平台：刷新三系统数据 → 计算 pendingItems
  │
  ▼
展示结果页
  ├── 基本信息
  ├── 三类病种待检清单（大字号、红/绿状态）
  └── 「已告知患者」按钮 → 写 remind_log
  │
  ▼
（可选）打印小票 / 语音播报「您还有 X 项检查未完成」
  │
结束
```

### 8.3 PDA 结果页 UI 原则

- **3 秒读懂**：待检项数量醒目，已完成绿色、待检红色
- **单手操作**：大按钮、少输入
- **弱网容错**：10s 超时显示缓存数据 + 「刷新」按钮
- **隐私**：30s 无操作自动返回首页，屏幕脱敏

### 8.4 PDA 专用 API

```
POST /api/v1/pda/scan          # 刷证查询 + 提醒
POST /api/v1/pda/remind/confirm # 确认已告知
GET  /api/v1/pda/today-stats   # 今日统计
```

## 9. 技术选型建议

| 层级       | 技术                                      | 理由                  |
| ---------- | ----------------------------------------- | --------------------- |
| 前端 Web   | Vue 3.5 + Vite 7 + TS + Element Plus      | 与现有项目一致        |
| 前端 PDA   | Vue 3 H5（Vant 或 Element Plus 移动适配） | 复用组件与接口层      |
| 后端       | Spring Boot 3.3 + MyBatis-Plus + MySQL 8  | 与现有 admin 模块一致 |
| 鉴权       | JWT + RBAC + 机构数据权限                 | 复用现有模式          |
| 任务调度   | Spring `@Scheduled` 或 XXL-JOB            | 增量同步              |
| 部署       | Nginx + JAR + MySQL                       | 政务内网常规部署      |
| 预留移动端 | 统一 REST API，后续 UniApp / 原生壳       | 一次后端多端复用      |

## 10. 非功能需求

| 类别         | 指标（建议值，待确认）                      |
| ------------ | ------------------------------------------- |
| PDA 刷证响应 | ≤ 3s（含源系统实时刷新）                    |
| Web 列表查询 | ≤ 2s（本地快照）                            |
| 并发         | PDA 50 台同时刷证                           |
| 可用性       | 99.5%（整合平台）；源系统故障时降级展示缓存 |
| 安全         | HTTPS、身份证加密存储、操作审计             |
| 备份         | 数据库日备，日志保留 ≥ 1 年                 |
