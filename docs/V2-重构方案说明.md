## 一、重构核心思路（一句话）

> **从"按人群分主线"重构为"按业务阶段聚合 + 按数据来源标签化"。**

V1：学校、重点、密接三条主线 × 每条主线 4 个子菜单（筛查 / 待诊断 / 潜伏 / 患者 / 历史）共 12+ 个相似页面。

V2：**业务阶段**作为顶层菜单，**数据来源**（学生 / 重点 / 常规 / 大疫情 / 推介 / 密接）变成统一列表中的一个"来源"字段。 密接因业务特殊（三轮独立筛查）保持独立菜单，但其"确诊患者"汇入统一的患者管理。

## 三、各模块业务逻辑详述

### 3.1 筛查管理（一级菜单）

#### 3.1.1 共性逻辑（与现有 V1 一致）

1. **筛查导入**：上传 Excel → 解析入库 → 自动判定 `is_latent`（阳性五项之一：PPD+/PPD++/PPD+++/EC阳性/IGRA阳性）
2. **待诊断**：仅对 `is_latent=1` 的数据进入待诊断列表
3. **待诊断列表操作**：
   - **追踪**（到位 / 未到位 / 其他，未到位最多 3 次）
   - **录入胸片结果**（独立按钮 ★ 改造点）
   - **录入诊断结果**（独立按钮 ★ 改造点，从原"录入胸片结果"中拆出来）
   - **转诊**（按现有 ReferralDialog 走分级诊疗流程）
4. **诊断结果分流**：
   | 诊断结果 | 流向 |
   |---|---|
   | 排除 / 其他 | 归档到对应筛查数据库 |
   | 疑似肺结核 | 保留在待诊断列表（继续后续处理） |
   | 潜伏感染者 | 进入**潜伏感染者管理**（聚合菜单） |
   | 确诊患者 | 进入**患者管理**（聚合菜单） |

#### 3.1.2 各筛查子模块差异

| 子模块 | 数据模板 | 现有页面 | 重构动作 |
|---|---|---|---|
| 学生筛查 | 学生模板表 V2.xlsx | `school/screening` + `school/suspected` | 路径与菜单重命名 |
| 重点人群筛查 | 重点人群表模板 V2.xlsx | `key-population/screening` + `suspected` | 路径与菜单重命名 |
| 常规筛查 ★ | 与重点人群完全一致（暂时复用） | 不存在 | **新建**（前端复用重点人群页面 / 后端表结构复制） |
| 大疫情导入筛查 ★ | 大疫情表.xlsx（详见 6.3） | 不存在 | **新建占位菜单**，导入后只需追踪+诊断（无筛查阶段） |

#### 3.1.3 ★ 改造点：胸片与诊断结果按钮拆分

**现状**：
- 待诊断页面中"录入胸片结果"按钮同时录入：是否进行胸片、胸片日期、胸片结果、**诊断结果**（4 个字段挤在一个弹窗内）
- 后端 API：`POST /latent/xray`（`submitXrayApi`）

**改造**：
- 拆为两个独立按钮：
  1. **录入胸片结果**（弹窗仅含：是否进行胸片、胸片日期、胸片结果）
  2. **录入诊断结果**（弹窗仅含：诊断结果，下拉选项=排除/疑似肺结核/潜伏感染者/确诊患者/其他）
- 操作流程：先录胸片 → 再录诊断（诊断必须在胸片之后才能录，由前端禁用控制）
- 后端：保留 `POST /latent/xray` 用于胸片；新增 `POST /latent/diagnosis` 用于诊断；或保留单接口但前端拆两步调用。

#### 3.3.3 ★ 改造点：首次随访 / 后续随访 增加备注 + 图片附件

**问题描述**（用户截图也佐证）：
- 之前的版本支持上传 2~6 张照片作为附件，"现在版本没有了"，需要找回。
- 后续随访已是多次填写（V1 已支持，`follow_up_visit.visit_seq`），但需要按用户提供的 Excel 模板字段对齐。

**改造方案**：
1. **首次随访 (`first_visit` 表)**：
   - 新增字段：`remark TEXT`（备注）
   - 新增字段：`attachment_urls TEXT`（JSON 数组，存图片 URL，2~6 张）
2. **后续随访 (`follow_up_visit` 表)**：
   - 已有 `remarks TEXT`，**改造现有 `attachment_url VARCHAR(512)` → `attachment_urls TEXT`（JSON 数组）**
   - 字段对齐用户附件 Excel "后续随访表"（具体字段待后续随访 Excel 模板确认；此处保留 JSON `visit_situation` 兼容存储）
3. 前端：弹窗中接入图片上传组件，限制 2~6 张，调用现有 `FileUploadController` 上传，回显时点击预览大图。

#### 3.3.4 ★ 改造点：患者数据删除功能

- 后端 `PatientController` 增加：
  - `DELETE /patient/{id}`（软删 + 级联软删 first_visit / follow_up_visit / medication_management / notice）
- 前端：患者管理列表每行操作列加"删除"按钮（按钮级权限 `patient:delete`）

#### 3.3.5 ★ 改造点：后续随访表样式（按用户给的 Excel 模板重建）

### 3.5 推介追踪管理（一级菜单，新增 ★）

#### 3.5.1 整体定位

新增的业务模块，用于**主动录入**待推介或待追踪的对象（区别于筛查导入的批量数据），手动驱动后续诊断与归档流程。

> **关于"推介给部门"vs"推介给用户"**：用户原文先后出现两种表述：  
> - "将数据推介给其它部门（与转诊几乎相同）"  
> - "录入后向系统内现有三、四级用户发起推介通知"  
>
> 本方案将两者**视为同一行为**：接收方在 UI 上选择"三/四级用户"，底层关联该用户所属部门。  
> 字段命名：`receiver_user_id`（三/四级用户ID）+ 自动派生 `receiver_dept_id`（用户所属部门ID）。

#### 3.5.2 两个子菜单的差异

| 子菜单 | 流程 |
|---|---|
| **推介** | 1. 手动录入待推介信息 <br/>2. 向系统内**三/四级用户**发起推介通知（底层关联其所在部门） <br/>3. 对方确认接收 / 否定接收 <br/>4. 推介接受后**可立即进入追踪**（推介人或接收人均可），也可对**已推介患者单独追踪** <br/>5. 追踪（到位 / 未到位 / 其他） <br/>6. 到位后补充：感染筛查、胸片、症状筛查等信息 <br/>7. 诊断（排除 / 确诊患者 / 潜伏感染者） |
| **追踪** | 1. 手动录入待追踪信息（无需经过推介环节） <br/>2. 直接追踪（到位 / 未到位 / 其他） <br/>3. 到位后补充：感染筛查、胸片、症状筛查等信息 <br/>4. 诊断（排除 / 确诊患者 / 潜伏感染者） |

> 区别：推介比追踪多了"向三/四级用户发起通知 + 对方确认"两步。  
> 用户原文："**推介后可以立即进入追踪，也可以对某个患者信息进行单独追踪**" — 即两个子菜单的追踪入口是互通的。

#### 3.5.3 诊断结果分流（同筛查）

| 诊断结果 | 流向 |
|---|---|
| 排除 | 归档（落入"常规筛查"数据库以备统计） |
| 确诊患者 | 进入聚合「患者管理」，`population_type='referral'` |
| 潜伏感染者 | 进入聚合「潜伏感染者管理」，`population_type='referral'` |

## 七、关键技术决策记录（ADR）

### ADR-1：是否物理拆分三条主线为聚合？

**决策**：物理拆分。前端路由全部重组，后端业务实体保留 `population_type` 字段不变，仅扩值。

**理由**：
- 现有 3 套 `latent / patient / history` 页面代码重复度极高（>85%），聚合后维护成本大幅下降。
- 后端无需拆表，向后兼容。

### ADR-2：常规筛查是否独立建表？

**决策**：**独立建表** `screening_regular`，结构复制 `screening_key_population`。

**理由**：
- 用户明确"常规筛查与重点人群完全一样，只是需要多加一个菜单并重新命名"。
- 数据来源不同，业务隔离更清晰；统计/导出/审计更方便。
- 后续若两者需要差异化字段，独立表更灵活。

### ADR-3：密接确诊患者如何并入聚合患者管理？

**决策**：密接业务在确诊时（`cc_status=1`）触发**写入 `patient` 表**（`population_type='closeContact'`），同时密接表保留原数据；聚合患者管理通过 `patient` 表查询所有患者。

**理由**：
- 解耦展示与存储，无需重构密接的 V4 三轮逻辑。
- 聚合查询性能更好（不需要 union 多表）。

### ADR-4：操作日志使用 AOP 还是 Filter？

**决策**：**AOP 切面 + 注解 `@OperationLog`**，登录单独硬编码。

**理由**：
- 大部分日志通过注解声明，灵活、零侵入业务代码。
- 登录涉及到鉴权前后切面执行顺序复杂，单独处理更稳。

### ADR-5：图片附件存储方案？

**决策**：沿用现有 `FileUploadController`（本地 `./uploads` 目录），URL 存数据库 JSON。后续视量级再决定是否切换 OSS。
